# Rubric: is this pull request ready to submit?

## Inputs

- **contributor-workflow:** AI-assisted. This is a fact about this course's contribution workflow, not something a package states. Change this line if the contributor works without AI assistance; the meets-repo-asks check reads it by name. It only decides whether a disclosure the repo asks for applies; it never adds a requirement the repo did not state.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | The diff's changed files and hunks, read against the plan's in-scope and out-of-scope statements, its named files, and its recorded deviation notes | Principle: the PR delivers the posted plan plus its recorded deviations, no more and no less. Pass if every changed file and hunk falls inside the plan's scope or a recorded deviation, and every planned change is in the diff or its omission is disclosed in the description with a reason. Fail if the diff changes something the plan leaves out or never mentions, with no deviation note, or drops a planned change without saying so. | required |
| description-matches-diff | Every claim the title and description make about the change (what changed, what was left out, how faithful it is to the plan), read against the diff and commits | Principle: the PR says truthfully what it does. Pass if every such claim is true of the diff. Fail if the description claims fidelity the diff contradicts (for example "exactly the plan, with no changes beyond it" beside an unrelated hunk), or describes a change the diff does not contain. A shortfall the description states plainly is a true claim and passes. | required |
| tests-shown | The PR's test evidence, read against the plan's main reproduction and each other step its test plan names (controls, extra failure modes, the repo's own checks or suite) | Principle: the evidence lets a stranger see the planned failure is gone. Pass if the plan's main reproduction is re-run as the plan names it, with observable output after the change (pasted output, an exit code, or a test count), and every other step the test plan names is reported as a specific result a stranger could check by re-running it (for example "`go test ./pkg/...` passes" or "the no-flag control is unchanged"). A named step that was not run passes only if the PR says so with a reason; a failing repo check passes only if it is shown and explained. Fail if the main reproduction is missing, replaced by a different case, or claimed only in prose; if a named step is silently missing; or if results are vague ("all tests pass", "works on my machine"). | required |
| diff-clean | The unified diff and the commit list | Principle: every hunk serves the change. Fail if the diff contains debug leftovers, commented-out or dead code, formatting-only churn, drive-by edits, dependency bumps the change does not need, or working notes such as plan or draft files. Otherwise pass. | required |
| meets-repo-asks | The repo's PR template sections, contributing asks, and contribution policy (eval: the repo-facts block; live: the PR template file and `CONTRIBUTING.md`), any explicit maintainer direction in the thread, and the **contributor-workflow** input, read against the title and description | Principle: the PR meets the repo's stated asks. Pass if every section the PR template asks for has real content (an honest "N/A" with a reason counts), every contributing ask that applies to this change is met (for example referencing the issue, a changelog entry, or tests), any disclosure the policy or template asks for appears, and explicit maintainer direction in the thread is engaged. The contributor-workflow input decides whether an AI-use disclosure the policy or template asks for applies (when it is AI-assisted, that disclosure must be present); it never creates a disclosure requirement by itself, so a repo with no AI-disclosure ask needs none. A repo with no template and no asks that apply to this change passes. | required |

## Verdict rule

Accept if every required check passes. Reject if any required check fails. Unclear counts as fail. Preferred checks never change the verdict.

## Notes on heuristics

- **Honest shortfalls:** a PR that does less than everything can still be ready. Each check above says what a disclosed shortfall does there: an omission disclosed with a reason passes diff-within-plan, a plainly stated shortfall is a true claim for description-matches-diff, and a step not run or a failing check passes tests-shown when it is disclosed and explained. The fail is for the silent version.
- **diff-within-plan:** whether a hunk is "inside the plan's scope" is a judgment call when the plan names an area rather than exact lines. The test is whether the plan's author would recognise the hunk as part of the planned change.
- **tests-shown:** the main reproduction needs observable output, meaning a reader can see the result (pasted output, an exit code, a test count), not a sentence saying it worked. Other named steps only need a specific, checkable report, the same "checkable, not just pasted" idea as the repro-check rubric. Which step is the "main reproduction" is a judgment call when a plan names several; it is the one that reproduces the issue's reported failure. A "before" may come from the plan's repro evidence instead of being re-run.
- **meets-repo-asks:** whether a contributing ask "applies to this change" is a judgment call; for example, a changelog ask may not apply to a test-only change. The AI-disclosure part reads the contributor-workflow input above instead of assuming it.
